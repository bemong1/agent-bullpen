# Changelog

Agent Bullpen is in **beta** (0.x): the formats it reads are the private on-disk transcripts of Claude Code and Codex, which can change with any release of those tools, and options and screens may change between 0.x releases. Please report what looks wrong with the bug template (it asks for the output of `python3 tools/harvest.py <session id>`, which holds no transcript text). `python3 server.py --version` prints the release you run.

## Unreleased

- **The activity timeline can look further back, and at a range of your own.** Besides 30 minutes, 2 hours, this debate and 12 hours there are 24 hours, 3 days, 7 days and all of the session (on a phone the longer ones are in a box next to the first four tabs), a custom range of two date-time inputs (at most 31 days, kept in the browser), and ◀ ▶ that move the range by its own length into the past and back toward now (the newest step stops at now; a range that ends in the past draws no "now" line and the live refresh does not move it). The server thins a window over 13 hours: for each lane one mark of each kind in each of about a thousand time columns (a number says how many a mark stands for), only the saved reports among the writes, and the 60 lanes that were most recently at work in the range until Show all (the window of a debate always holds the debate's own agents; a session with hundreds of agents stays under 1 MB, and the server's lock is held for milliseconds, not for the binning); the windows up to 12 hours are sent as before. `/api/timeline` takes an optional `until` (a number after `since`, at most 31 days later, else `400` with `error_code` `bad_range`) and `all=1`. Ticks are every 12 hours and every day at local noon and midnight (counted on the calendar, so a change of the clocks does not move them), with dates over a day, as many of them as the width of the card allows. "Up to now" is an open end: a range picked or stepped to now goes on with the clock, and one that ended a few minutes ago is asked for again for the records that come late.
- **The debates an orchestrator makes itself are listed on its page.** What the orchestrator itself wrote and it worked (Claude Code: `Write`, `Edit`, `MultiEdit` and a `Bash` redirect, `tee` or `mkdir` whose result was not an error; Codex: a completed `FileChange` that added or changed a file, and a command that exited 0) points the list at that folder, and it is listed when the disk says it is a debate: a guide (`brief.md`, `README.md`, `index.md`) with exact round folders (`r1`, `round2`), or a `brief.md` that names two result files or more. Before, a folder the orchestrator made in a scratch place and no linked run wrote into was missing until something else named it. It is only the list: no seat, no room and no member comes from it, and a `brief.md` alone, a plan or a note, a README at the top of a repository or in its `docs`, the folders Claude Code and Codex keep for themselves and this program's own repository are not listed this way. The page keeps the 64 latest folders (`listing_capped` in Diagnostics says more were written). A write or `mkdir` the shell may not have run (after `||`, in an `if`, `case` or `while`, inside a `{ }` group, a subshell or a function that may not have run, in a `for` over nothing, after an `exit`, `return` or `exec`, `mkdir --help`) does not count, the page keeps the folders written last, a debate with no agent in it (listed by these writes or by the walk of the repository) comes behind the debates that have agents, and one listed only by these writes shows in its group only what passed the gate. Writes by agents (a nested `claude -p`, a Codex sub-agent's `apply_patch`) do not count yet.
- **A running `codex exec` of a Codex orchestrator takes its debate seat while it runs (Linux).** The record of the command that started it is written only when the command ends, so a foreground child whose report path was given with `-o` (and not in its instruction) had no seat until then. The seat is now planned from the command line of the child's own process (`-o FILE` or `--output-last-message FILE`, an absolute path, exactly one, only for a child already linked by its environment or process, and only when the processes that have its transcript open agree); the command record replaces it when it comes. It links nothing and is not kept in `links.json`. A relative `-o`, a `>` redirect of a `claude -p`, and macOS still take the seat after the command ended.
- **Fix: a Python file run by its own path.** `./relay.py` (or `$R/relay.py`, an absolute path) whose first line names python is read as code, like `python3 relay.py`: only a call that hands `claude` or `codex` to a command starts a run, a mention is a guess, and a file that only types the words into a window starts nothing.
- The office card starts open from a window width of 768 px (a tablet) instead of 1500 px, and a collapsed office (a phone, or a choice you made) says so in one line inside the card; pressing the line opens it. On an iPad the card used to start collapsed with nothing to tell why.

### Known limitations

- A running participant whose report path is known only from a shell `>` redirect or a relative `-o`, and any running `codex exec` on macOS (no `/proc` to read its arguments), takes its debate seat once its run is over and its record says where the report went.
- On macOS a `codex exec` started by a Codex orchestrator is linked once its command record is written (when the command ends); while it runs it shows as a session of its own.

## 0.2.0 — Codex sessions as orchestrators

- **A Codex orchestrator's page gathers its team like a Claude one.** The runs a Codex thread starts are cards on its page, whoever started them: its native sub-agent threads (named by the end of their path, with their own state and tokens), the `claude -p` and `codex exec` runs its shell started (and those started by a sub-agent's shell, hanging under that sub-agent), and the runs those started in turn. They are found from what Codex records: the sub-agent events in the parent's transcript, the command records (`CommandExecution`: the command text and folder, written when the command ends) and the `CODEX_THREAD_ID` / `CODEX_SESSION_ID` its shells leave in the environment of a child. Debates are seated from these runs as for a Claude orchestrator, and the diagnostics count a launch that left no record (`orphan_launch`).
- **The conversation of native sub-agents**: the spawn, the messages between agents and a sub-agent's final report appear as cards. The instruction a sub-agent got is ciphertext in the record, so its spawn card says so instead of showing it; the card of the final report is the first message a sub-agent sends after it is done.
- **State of a sub-agent**: its own transcript says how its turn ended (done, an error, interrupted); an interrupt that its parent recorded after it had finished changes nothing; one that came while it worked makes it *interrupted*; a turn that is open when the Codex process of its orchestrator is gone is *ended*.
- **Tokens**: a sub-agent's tokens are on its own card, not in the orchestrator's approval-review (guardian) tokens; the page total is the same as before (nothing is counted twice). The history that Codex copies from the parent into the front of a sub-agent's transcript is not read as the sub-agent's own turns, activity or instruction.
- **Fix: a session that only relays an instruction is no launcher.** A Claude session that passed an instruction on as text was taken for the parent of the run that got it. Words now count as a launch only where something runs them: a command position, or the command line a program that runs its arguments is given (read once, as one command). So `tmux send-keys`, `screen -X stuff`, `echo`, an argument of an ordinary program (`curl --data …`), the same through `xargs`, `ssh` or `kubectl exec`, a script that only types the words, and a Python file that only types them (Python files are read as code: only a call that hands `claude` or `codex` to a command starts it) start nothing. `links.json` is format 6; the content links of older formats are worked out again from the transcripts.
- **Fix: environment of two providers.** A `claude -p` run started by the shell of a `codex exec` run that Claude started names both providers in its environment; it is placed under the run that started it, not under the top Claude session.
- **Fix: names left in an environment.** A tmux server keeps the environment of the shell that started it, so a run started through it can carry the names of a session or thread that did not start it. When the session or thread they name ran nothing then that could have started the run, and another session's recorded launch fits the run's instruction, the names count for nothing and `evidence_conflict` says so; without such a launch they still settle the run. Names of a Codex thread the dashboard does not know make a match of the instruction text a guess, not a certain link.
- **Fix: the title of a run linked from `links.json`.** After a restart, a `claude -p` run whose parent came from the saved links could show the description of another call, or only `claude -p`; the call that started it is now read from the instruction text within that parent, and the card is titled again once it is known. A run started again by the same command whose output file names only the newest session is given the call that started it, not the first one.
- **Fix: a debate seat is taken over from a run that was cut off.** When a participant's run stopped half way (a `claude -p` closed with its process record and no end of turn, shown as *interrupted*) and the same script was run again with the same instruction (a new session), both runs claimed the seat, it was held (`seat_tie_held`) and neither showed in the debate table. The later run now takes the seat when the earlier one made no record after the later one started. If the cut-off run is resumed and works at the same time, the seat is still held, and a report it writes is a claim like any other.
- **A Claude orchestrator's `claude -p` runs show their own Agent-tool sub-agents** under them (and the session list counts them).
- The link line of a run a Codex thread started says `exec` and its time where a Claude launcher's says `Bash`; a session opened by the id of a run or thread that something started opens the page of the top orchestrator.
- Diagnostics: Codex records of a shape the dashboard cannot read (a thread of an unknown kind, command records it could not parse) are `format_drift`.
- Tools: the scenario generator has a bundle for this (`--cases 'cxo:*'`), `tools/synth_home.py --codex-orch` makes a Codex orchestrator HOME, and `tools/regress/codex_checks.js` checks its page.

### Known limitations

- A Codex shell ends the child of a `&` (or `nohup … &` without `setsid`) when the call returns: nothing is left to link, and the launch shows only as an `orphan_launch` count in Diagnostics. A child started with `setsid nohup … &`, in the foreground or in a Codex PTY session is found.
- The JavaScript of a Codex code-mode cell (`exec` with `tools.exec_command({cmd: …})`) is not interpreted: what a thread ran is known from Codex's own `CommandExecution` records, which are written when the process ends (so a command still running, or one that outlived its turn, has no text yet).
- The instruction of a native sub-agent is encrypted in the transcript: its card names it by its path and says the instruction cannot be shown; nothing is matched on it.
- A foreground `codex exec` that the orchestrator's shell started and that is still running has no command record yet (it is written when the command ends): it is linked by its environment or process, but it takes its seat in a debate table once its command has ended.
- A debate is found from the transcripts of the agents and from the repository the agents work in; the orchestrator's own writes to a folder (a `talk/brief.md` it makes before it starts anyone) do not find one by themselves.
- A Codex thread that is a sub-agent but whose transcript does not say where the history copied from its parent ends is not shown (`format_drift`).

## 0.1.0 — first public release

- A live, read-only view of Claude Code and Codex sessions: the orchestrator, its sub-agents, `claude -p` and `codex exec` runs it started (grandchildren under their launcher), with status, current tool, context use, model and an API-price cost estimate.
- Who launched whom from evidence: sub-agent metadata, the child's session id in the launch's output file, process lineage and environment, the instruction text matched against a running launch; guesses are marked as such and ambiguous cases are held instead of guessed. Unlinked candidates and a diagnostics list show what could not be decided.
- Debates and other group work from the disk: topic × round × participant tables for debate folders (`brief.md`, `r1/`), with final reports found automatically; people who work together in a folder without that shape (a meeting with an agenda, a brief, a README) get a room of their own.
- Run status per run: working, done, failed, interrupted (usage limit with reset time, API error, time limit, exited early), unknown, and an orchestrator waiting for a usage limit; limit and API-error lines appear as system lines, not as the orchestrator's words.
- Plan bar: Claude usage from Claude Code's own status line (`statusline.py`; no network request, no token) or the `.claude.json` cache, Codex usage from its rollouts. The dashboard never calls Anthropic and has no code that reads a login or token.
- Reach it from other devices: `--host` takes any address or host name (`0.0.0.0`, `::`, a LAN or VPN address). Every address that is not loopback requires an access token: random at each start and printed with the addresses to open (`--token` or `AGENT_BULLPEN_TOKEN` fixes it, `--no-auth` switches the check off with a loud warning). The first visit with the token sets an `HttpOnly`, `SameSite=Strict` cookie and removes the token from the address; without the token or the cookie every page and API answers 401. Loopback needs no login, and its `Host` allow list stays. An SSH tunnel needs no option.
- One folder, one debate: the same folder reached by a link, and the copies of a repository's folder in its linked worktrees, are listed once (the copy your agents work in stands for them); an instruction-only folder inside another debate is no debate of its own. A room or a review without rounds says "Done" once every seat has handed in and nobody works, and a conclusion document of the bundle (`CLOSING.md` …) closes the topics it names.
- Pixel-art office view (people walk in through the door when they arrive, also when their arrival rearranges the rooms), agent talk card, timeline, English and Korean UI (one dictionary file per language).
- Tested on Linux (Python 3.9+), with a scenario generator that checks the board against independently computed answers; the test suite never reads your real home or `~/.cache`. macOS is experimental: the unit tests run there in CI, but it is not yet verified on a Mac.

### Known limitations

- (0.1.0) The team view assumed a Claude Code orchestrator: runs that a Codex orchestrator started from its shell were not gathered under it. This is no longer so; see 0.2.0 above for what a Codex orchestrator's page can and cannot show.
- macOS is experimental (unit tests in CI, not yet verified on a Mac); native Windows is not supported.
